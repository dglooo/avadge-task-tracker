# task-tracker — скилл для работы с трекером задач через MCP

Скилл для Claude Code / Claude Agent SDK: описывает, как ассистент работает с
task-трекером — как классифицировать задачу, как писать её текст, чем доказывать
выполнение и где проходит граница между тем, что закрывает модель, и тем, что
принимает человек.

## Установка

```bash
git clone <этот-репозиторий> ~/.claude/skills/task-tracker
```

Либо положить папку в `.claude/skills/task-tracker/` внутри проекта — тогда скилл
виден только в нём.

Проверка: `/task-tracker` в Claude Code.

## Что внутри

`SKILL.md` — единственный файл. Frontmatter (`name`, `description`) определяет,
когда скилл подхватывается автоматически; тело — инструкция.

## Идея, которую скилл описывает

Трекер, в котором работают и люди, и модели, ломается двумя способами.

**Первый: тип задачи — свободная строка.** За три дня в реальном трекере
завелось четырнадцать типов, из них семь — синонимы (`seo_fix`, `markup_fix`,
`content_fix`, `seo_rewrite` — четыре имени для «поправить контент»). Пока тип
ни на что не влияет, это терпимо. Как только к нему привязана приёмка — «какой у
задачи тип» перестаёт быть вопросом с одним ответом.

Лечится строгим перечислением, где тип отвечает на один вопрос: **чем будет
доказано, что задача сделана.**

**Второй: приёмка одна на все задачи.** Если каждая задача обязана пройти через
подтверждение модели и нажатие человека — включая «написать отчёт» и
«переставить цифру в админке», — то остановка, которую нельзя пропустить, но и
провести нечем, превращается в ритуал. Её проходят не глядя, и она перестаёт
что-либо гарантировать.

Лечится тремя режимами приёмки, привязанными к типу:

| режим | смысл | кто закрывает |
|---|---|---|
| `self` | проверяется запросом к сайту | модель, приложив запись о проверке |
| `eye` | нужны человеческие глаза (вёрстка, ощущение) | человек |
| `none` | проверять нечего | кто сдал |

Режим — свойство **типа**, а не задачи. Будь он полем задачи, его выставлял бы
тот же, кто задачу сдаёт, и гарантия исчезла бы.

## Требования

MCP-сервер с группой инструментов `tasks_*`:
`list_tasks`, `get_task`, `create_task`, `update_task`, `edit_task`,
`attach_artifact`, `get_artifact`, `get_seo_page`, `propose_seo_changes`.

Скилл написан под конкретную реализацию (Django + DRF + FastMCP) и содержит
названия её типов и полей. Под другой трекер переносится правкой таблиц типов и
списка инструментов; конструкция «тип → режим приёмки → кто закрывает» от
реализации не зависит.
