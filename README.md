# avadge-task-tracker — скилл работы с трекером задач AVADGE через MCP

Скилл для Claude Code / Claude Agent SDK: описывает, как ассистент работает с
task-трекером — как классифицировать задачу, как писать её текст, чем доказывать
выполнение и где проходит граница между тем, что закрывает модель, и тем, что
принимает человек.

## Установка

```bash
git clone https://github.com/dglooo/avadge-task-tracker ~/.claude/skills/avadge-task-tracker
```

Либо положить папку в `.claude/skills/avadge-task-tracker/` внутри проекта — тогда скилл
виден только в нём.

Проверка: `/avadge-task-tracker` в Claude Code.

## Что внутри

`SKILL.md` — единственный файл. Frontmatter (`name`, `description`) определяет,
когда скилл подхватывается автоматически; тело — инструкция.

## Идея, которую скилл описывает

Трекер, в котором работают и люди, и модели, ломается двумя способами.

**Первый: тип задачи — свободная строка.** За три дня в реальном трекере
завелось четырнадцать типов, из них семь — синонимы (`seo_fix`, `markup_fix`,
`content_fix`, `seo_rewrite` — четыре имени для «поправить контент»). Пока тип
ни на что не влияет, это терпимо. Как только к нему привязана приёмка — «какой у
задачи тип» перестаёт быть вопросом с одним ответом.

Лечится строгим перечислением, где тип отвечает на один вопрос: **чем будет
доказано, что задача сделана.**

**Второй: приёмка одна на все задачи.** Если каждая задача обязана пройти через
подтверждение модели и нажатие человека — включая «написать отчёт» и
«переставить цифру в админке», — то остановка, которую нельзя пропустить, но и
провести нечем, превращается в ритуал. Её проходят не глядя, и она перестаёт
что-либо гарантировать.

Лечится тремя режимами приёмки, привязанными к типу:

| режим | смысл | кто закрывает |
|---|---|---|
| `self` | проверяется запросом к сайту | модель, приложив запись о проверке |
| `eye` | нужны человеческие глаза (вёрстка, ощущение) | человек |
| `none` | проверять нечего | кто сдал |

Режим — свойство **типа**, а не задачи. Будь он полем задачи, его выставлял бы
тот же, кто задачу сдаёт, и гарантия исчезла бы.

**Третий: работу принимает кто попало.** Когда к трекеру подключено несколько
ассистентов, задачу, которую поставил один, принимает другой — тот, кто первым
зашёл в очередь на проверку. Контекста постановки у него нет: он видит отчёт
исполнителя и соглашается с ним. Приёмка снова становится формальностью, теперь
уже незаметной — в поле стоит `done`, и со стороны это выглядит как проверенная
работа.

Лечится постановщиком: задача помнит API-ключ, по которому заведена, и решения о
приёмке — принять, вернуть на доработку, снять — доступны только этому ключу или
человеку. Сама работа остаётся общей: взять, сделать и сдать на проверку может
любой. Ключ удобен тем, что это единственная стабильная личность вызывающего:
имя модели меняется, сессия живёт часами, ключ выдаётся один раз на клиента.

**Приоритет приходится описывать так же явно.** Модель, которой поручено следить
за сайтом, помечает критическим всё заметное: непонравившийся отступ получает тот
же уровень, что и упавшая форма заявки. Если по критическим уходит уведомление
человеку, через неделю их перестают читать. Поэтому приоритет привязан к
последствиям, а не к заметности, и прямо сказано, что дизайнерские пожелания
критическими не бывают.

## Требования

MCP-сервер с группой инструментов `tasks_*`:
`whoami`, `list_tasks`, `get_task`, `create_task`, `update_task`, `edit_task`,
`post_message`, `attach_artifact`, `get_artifact`, `get_seo_page`,
`propose_seo_changes`.

`whoami` отдаёт имя и префикс ключа вызывающего, `list_tasks` принимает фильтр
`owner` (`me`, префикс чужого ключа, `none`). Без них постановщик не работает:
модель не знает, кто она, и не может отобрать свою очередь на приёмку.

Скилл написан под конкретную реализацию (Django + DRF + FastMCP) и содержит
названия её типов и полей. Под другой трекер переносится правкой таблиц типов и
списка инструментов; конструкция «тип → режим приёмки → кто закрывает» от
реализации не зависит.
