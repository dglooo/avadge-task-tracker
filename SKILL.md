# Task-трекер AVADGE

Одна таблица задач на всех: чекеры находят автоматически, человек ставит руками,
ассистент заводит по итогам аудита. Панель — `https://avadge.com/management/tasks`,
инструменты — MCP-сервер `avadge`, группа `tasks_*`.

Девять вещей, из-за которых чаще всего получается брак. Если ты прочитаешь только
это, прочитай хотя бы это:

1. **Ты — это твой API-ключ, и принимаешь ты только СВОИ задачи.** Постановщик
   задачи — ключ, по которому она заведена. `done`, `confirmed`, `dropped` и
   возврат в `open` на чужой задаче — 403. Начни сессию с `whoami`. Подробности —
   в разделе «Постановщик: чью задачу ты вправе принять».
2. **Приоритет — про то, что сломано, а не про то, что хочется.** `critical` —
   сайт или деньги не работают прямо сейчас. Дизайн-хотелки никогда не
   `critical`. Сомневаешься — ставь ниже. Раздел «Приоритет».
3. **Тип задачи выдумывать нельзя.** Их ровно двенадцать. Тип определяет, кто
   вправе принять работу, поэтому синоним — не мелочь.
4. **Закрывая задачу, прикладывай `verified`** — чем именно проверял. Без него
   сервер откажет, и правильно сделает.
5. **Проверяется ТОЛЬКО боевой сайт `https://avadge.com`.** Локальный сервер,
   собранный фронт и «у меня в докере работает» доказательством не являются
   вообще. Подробности — в разделе «Проверка идёт на боевом, и только на нём».
6. **Вёрстку и новую функциональность ты не закрываешь.** Твой максимум —
   `confirmed`. Кнопку жмёт человек.
7. **Изменил формулировку задачи — правь тело через `edit_task`**, не пиши новую
   редакцию в `note`. Иначе описание раздвоится.
8. **Код в репозитории правит только ответственный исполнитель.** Ты пишешь ТЗ,
   а не коммит. Подробности — в разделе «Фронтенд и правки в коде».
9. **Спорный вопрос — не повод гадать.** Есть статус `discussion` и реплики.
   Но и не повод не работать: вопрос, на который можно ответить, сходив и
   посмотрев, — не спорный.

## Как выбрать тип

Тип отвечает на ОДИН вопрос: **чем будет доказано, что задача сделана.** Не «про
что она», а «как проверить». Выбирай по способу проверки — тогда режим приёмки
получится сам собой.

В квадратных скобках — режим приёмки, см. следующий раздел.

### Контент — проверяется чтением ответа сервера

| тип | когда | проверка |
|---|---|---|
| `seo_meta` [self] | title, description, H1, seo_text, **живущие в строке SeoPage** | запросить страницу, сверить поля |
| `content_text` [self] | видимый текст и заголовки: стоп-слова, «О компании», FAQ, H1/H2 в шаблоне | запросить страницу, найти текст в HTML |
| `seo_tech` [self] | JSON-LD, Open Graph, canonical, robots.txt, sitemap | распарсить ответ, проверить блок |

Развилка `seo_meta` vs `content_text` решается одним вопросом: **правка ложится в
SeoPage или в шаблон?** Если в SeoPage — `seo_meta`, и тогда работает
`propose_seo_changes` и кнопка «Применить». Если текст захардкожен в шаблоне —
`content_text`, и правку вносят в коде. Посмотри `get_seo_page(path)` перед тем,
как решать: строки может просто не быть.

### Код — меняется поведение сайта

| тип | когда | проверка |
|---|---|---|
| `page_create` [self] | новая страница, лендинг, карточка модели | адрес отдаёт 200, обязательные элементы из ТЗ на месте |
| `bug` [self] | сервер отдаёт не то: 500 вместо 404, мягкая 404, нули в HTML, неверный расчёт | воспроизвести запросом |
| `ui` [**eye**] | вёрстка, адаптив, поведение в браузере | глазами человека на трёх ширинах |
| `performance` [self] | вес страницы, скорость, CWV | замер |
| `feature` [**eye**] | новая функциональность | глазами человека |
| `refactor` [self] | переезд кода без изменения поведения | поведение не изменилось |

### Не код — на сайте ничего не меняется

| тип | когда | проверка |
|---|---|---|
| `research` [none] | узнать и записать: замеры, сверки, GEO | отчёт написан |
| `plan` [none] | навигатор, очередь работ, порядок задач | пункты разошлись по задачам |
| `data` [none] | заполнить данные в админке | поле заполнено |

### Типы чекеров

`car_no_buyout_price`, `page_noindex`, `schema_report_relay` и подобные — это
имена чекеров, они тоже валидные значения `kind`. **Заводить такие задачи руками
не надо**: их создаёт и закрывает сам чекер, когда условие появляется и исчезает.
Ты их только читаешь и выполняешь.

## Приоритет: что сломано, а не что хочется

Приоритет отвечает на вопрос **«что случится, если это не сделать сегодня»**.
Не «насколько это важно заказчику» и не «насколько это заметно».

| приоритет | когда | примеры |
|---|---|---|
| `critical` | сайт или деньги **не работают прямо сейчас** | 500/502, раздел или главная недоступны, форма заявки не отправляет, калькулятор считает неверную цену или пошлину, потеря данных, дыра в безопасности, сайт выпал из индекса |
| `high` | работает, но **бьёт по трафику или деньгам** | `noindex`/битый canonical на важной странице, сломанный виджет на ключевой странице, мобильная вёрстка непригодна к использованию, чекер сообщил о регрессии, пропали цены в каталоге |
| `normal` | **по умолчанию.** Надо сделать, никто не горит | новый текст, FAQ, JSON-LD, новая страница, обычный баг без последствий для выдачи |
| `low` | косметика и пожелания | отступы, цвета, «сделать красивее», рефакторинг, неспешные исследования |

Три правила, которые нарушают чаще всего:

1. **Дизайн-хотелки — никогда `critical` и почти никогда `high`.** «Переставить
   блок», «поменять шрифт», «не нравится кнопка» — это `low` или `normal`, даже
   если просят очень настойчиво. `critical` — только когда что-то **сломано**:
   не открывается, не отправляет, считает неверно, отдаёт ошибку.
2. **Сомневаешься — ставь НИЖЕ, не выше.** Заниженный приоритет человек поднимет
   одним кликом. Завышенный обесценивает всю очередь: когда `critical` стоит на
   половине задач, настоящий пожар в ней не виден.
3. **`critical` и `high` будят человека.** По ним уходит уведомление в Telegram.
   Каждый ложный `critical` — это человек, который бросил дела и открыл сайт зря.
   После третьего раза уведомления перестанут читать, и настоящий пожар пройдёт
   незамеченным.

Тест перед постановкой `critical`: **можешь ли ты назвать адрес, который прямо
сейчас отдаёт не то, и код ответа?** Не можешь — это не `critical`.

## Режимы приёмки: кто закрывает задачу

| режим | типы | твой максимум |
|---|---|---|
| `self` | seo_meta, content_text, seo_tech, page_create, bug, performance, refactor | `done` + обязательный `verified` |
| `eye` | **ui, feature** | `confirmed`. Дальше человек |
| `none` | research, plan, data, находки чекеров | `done` без `verified` |

Почему так. Раньше любая задача обязана была пройти через подтверждение и нажатие
человека — включая «написать отчёт» и «переставить цифру в админке». Проверка,
которую нельзя пропустить, но и провести нечем, превращается в ритуал: её
выполняют не глядя, и она перестаёт что-либо гарантировать. Остановка теперь стоит
там, где её действительно есть кому пройти, а вместо неё в остальных случаях —
запись о том, что ты проверил.

### Что считается записью о проверке

`verified` — это **воспроизводимый факт**, а не самооценка.

Годится:
> `GET /about-company/` → 200. В HTML `<title>О компании AVADGE — автосалон и
> импорт автомобилей в Москве`, 59 знаков. H1 совпал с предложенным побайтово.
> Строка SeoPage в базе содержит то же значение.

Не годится:
> Проверил, всё хорошо. Задача выполнена.

Второе — это отсутствие проверки, записанное словами. Если проверить нечем —
значит тип выбран неправильно, и это `eye` или `none`.

## Постановщик: чью задачу ты вправе принять

К MCP подключено несколько ассистентов, и у каждого **свой API-ключ**. Ключ —
единственная стабильная личность вызывающего, поэтому он и есть постановщик:
задача, заведённая по ключу, помнит этот ключ в поле `owner` (имя и префикс).
Задачи человека и находки чекеров постановщика не имеют.

Правило одно: **решения о приёмке принимает постановщик или человек.** Решения
о приёмке — это четыре перехода:

* `done` — принять;
* `confirmed` — принять со своей стороны и передать человеку;
* `open` из `review`/`applied`/`confirmed` — вернуть на доработку;
* `dropped` — снять.

Чужой ключ на любом из них получает 403, и в тексте ошибки названы оба ключа:
чей это ключ и чья задача. Всё остальное — взять в работу, `review`,
`discussion`, `backlog`, реплики, артефакты, правки тела — доступно любому ключу:
это работа, а не приёмка.

Почему так. Раньше задачу, которую поставила одна нейронка, принимала другая —
та, что первой зашла в очередь `review`. У неё не было контекста постановки,
она видела отчёт исполнителя и соглашалась с ним. Приёмка превратилась в
формальность, и невалидная работа уходила в `done` с отметкой «проверено».

Что из этого следует для тебя:

1. **Начинай сессию с `whoami`.** Он отдаёт имя и префикс твоего ключа. Не
   угадывай, кто ты, по 403.
2. **Твоя очередь на приёмку — `list_tasks(owner="me", status="review")`**
   (и `applied` для `seo_meta`). Это задачи, которые поставил ты и которые
   сдали. Их принимаешь ты, и никто другой этого за тебя не сделает.
3. **Чужая задача у тебя в работе — доводи до `review` и остановись.** Отчёт в
   `note`, `verified`-факты — тоже в `note`, чтобы постановщику было что
   проверить. Принимать будет он.
4. **Задача без постановщика** (`owner: null` — от человека или от чекера)
   принимается по прежним правилам: `[self]` закрываешь сам с `verified`,
   `[eye]` до `confirmed`.
5. **Не заводи задачу заново, чтобы стать её постановщиком.** Это дубль, и он
   виден: две задачи с одним текстом, одна из них не в твоём `owner`.

## Проверка идёт на боевом, и только на нём

**Единственный сайт, на котором задача считается проверенной, —
`https://avadge.com`.** Всё остальное — черновик:

* локальный сервер в докере, включая `https://localhost/` с `Host: avadge.com`;
* пересобранный `npm run build` и свежие файлы в `staticfiles/vite/`;
* правка в шаблоне, которая «точно применится»;
* закоммиченная и даже запушенная ветка.

Ничто из этого не меняет боевой сайт. Между «сделано у меня» и «сделано»
стоят коммит, пуш, слияние в ту ветку, которую разворачивают, и сама
выкатка с пересборкой контейнера. Пока это не прошло, человек, открывший
сайт, видит СТАРУЮ версию — и правильно считает, что задача не сделана.

Отсюда правила:

1. **Ни `done`, ни `confirmed` не ставятся по локальной проверке.** Пока правка
   не на бою, максимум — `review` с отчётом, где прямо сказано: сделано
   локально, ждёт выкатки.
2. **В `verified` пиши боевые адреса.** `GET https://avadge.com/catalog/` и что
   именно пришло в ответе. Замер с localhost в `verified` — это ложь, даже если
   ты честно его снял.
3. **Отличай бой от локального по данным, а не по вкладке.** Числа в каталоге,
   свежие карточки, счётчики — на локальной базе они другие. Если счётчик
   говорит одно, а на скриншоте человека другое — ты смотрел не туда.
4. **Проверь, что выкачено именно то.** После деплоя запроси боевую страницу и
   найди в ответе конкретный признак правки: новый класс, убранный текст,
   новый блок. «Задеплоил» без такой проверки — не проверка.
5. **Отчёт о локальной работе пиши так, чтобы это нельзя было прочитать как
   «готово на сайте».** Формулировка «сделано и собрано локально, на боевом
   пока прежняя версия» — обязательна, а не любезность.

Так уже было: три задачи ушли в `confirmed` по замерам на локальном сервере,
человек открыл боевой сайт и увидел прежнюю вёрстку. Формально в отчёте
стояло «ждёт выкатки», по факту статус говорил «принимай». Статус важнее
примечания — его и читают.

## Поток работы

```
open ──► review ──► done            типы [self] и [none]
                     ▲
                     └── verified обязателен для [self]

open ──► review ──► confirmed ──► done      типы [eye]
                    (ты)          (человек)

open ──► review ──► applied ──► done        только seo_meta
                    ▲
                    └── кнопку «Применить» жмёт ЧЕЛОВЕК

любой рабочий статус ──► discussion ──► open | review
                                         ▲
                                         └── вывод обязателен
```

Возврат в работу (`open`) из `applied`/`confirmed` требует непустой причины: что
именно доделать. Снятие (`dropped`) — тоже. Выход из `discussion` — вывода.

### Обычный круг

0. `whoami` — кто ты. Один раз в начале сессии.
1. `list_tasks(assigned_to_llm=true, status="open")` — твоя очередь.
2. `get_task(id)` — целиком, включая `entity`, `owner` и опись файлов. Читай
   **до** того, как что-то предлагать: в `entity` лежат данные находки, в
   `owner` — кто будет принимать.
3. `update_task(id, assigned_to_llm=true)` — взять себе. По одной. Задача,
   помеченная твоей и брошенная в `open`, для человека выглядит как работа,
   которая идёт, хотя её никто не делает.
4. Сделать работу.
5. Сдать:
   * `seo_meta` → `propose_seo_changes(...)`, задача уходит в `review` сама;
   * остальное → `update_task(id, status="review")` плюс отчёт в `note`.
6. Принять — **только если `owner` — это ты или `owner: null`**:
   * `[self]` → `update_task(id, status="done", verified="...")`;
   * `[eye]` → `update_task(id, status="confirmed")` и остановиться;
   * `[none]` → `update_task(id, status="done")`.
   Чужая задача — остановись на шаге 5.

### Приёмка своих задач на `review` и `applied`

`list_tasks(owner="me", status="review")` — это работа, которую сдали тебе и
которую никто, кроме тебя, не примет. У тебя два выхода, и оба твои:

* сходил, проверил на бою, всё на месте → `done` (или `confirmed` для `[eye]`);
* сходил, проверил, чего-то не хватает → `open` + `note` с тем, **что именно**
  доделать.

Молча оставить задачу висеть — третьего выхода нет. Именно так задачи копятся:
каждая по отдельности «вроде на проверке», а вместе — очередь, которую никто не
разбирает. Раньше её разбирал кто попало, и это было хуже.

Задачи без постановщика (`owner: null`) в `review` — тоже твои: их принимает
любой ассистент по прежним правилам.

## Подзадачи: большая работа с пунктами внутри

Когда одна работа распадается на однотипные пункты — заводи родителя и
подзадачи, а не одну задачу со списком в теле.

```
create_task(title="Добавить FAQ на страницы услуг", kind="plan")        → #80
create_task(title="FAQ на /services/turnkey-delivery/",
            kind="content_text", parent_id=80)
create_task(title="FAQ на /services/car-selection/",
            kind="content_text", parent_id=80)
...
```

Зачем это, а не список пунктов в описании:

* **пункты не теряются.** Родителя нельзя закрыть, пока жива хоть одна
  подзадача — сервер откажет и назовёт номера. Список в теле такой гарантии не
  даёт: закрыл родителя, три пункта из восьми исчезли вместе с ним;
* **у каждого пункта свой тип и своя приёмка.** «Добавить FAQ» — это
  `content_text`, а «переверстать блок FAQ» — `ui`, и принимают их разные люди.
  Внутри одной задачи это не выразить;
* **работать можно параллельно** и видеть, сколько осталось.

Правила:

* **уровень вложенности один.** Подзадачи у подзадачи не бывает, сервер
  откажет. Понадобился третий уровень — значит родитель на самом деле два
  разных родителя;
* **родитель обычно `plan`**, но не обязательно: если у большой работы есть
  собственный проверяемый результат, ставь тип по нему;
* `list_tasks(parent=80)` — подзадачи одной задачи,
  `list_tasks(parent="none")` — только верхний уровень;
* подзадачи и их статусы приходят в `get_task(id)` полем `subtasks`.

Не дроби ради дробления. Две подзадачи — обычно просто одна задача. Восемь
однотипных — то, ради чего это сделано.

## Обсуждение: спорный вопрос

Статус `discussion` — для случая, когда работать по задаче нельзя не потому,
что некому, а потому, что **неизвестно что**: ТЗ противоречит само себе, два
решения выглядят одинаково разумно, или выбор делать не тебе.

Задача в `open` выглядит как «бери и делай». Человек берёт её и через двадцать
минут упирается в тот же вопрос, в который упёрся ты. Поэтому вопрос паркуется
отдельным статусом, а не остаётся строчкой в отчёте.

Порядок:

```
update_task(id, status="discussion")
post_message(id, "В чём вопрос, какие варианты, чем отличаются,
                  что рекомендую и почему")
        ← человек отвечает своими репликами
update_task(id, status="open", note="<ВЫВОД>")
edit_task(id, body="...")     ← если по итогам поменялось ТЗ
```

Что важно:

* **выйти из обсуждения без вывода нельзя.** Сервер требует непустой вывод, и
  это не формальность: обсуждение без вывода через неделю начнётся заново с
  того же места. Вывод — это «к чему пришли и что теперь делать»;
* **вывод не заменяет ТЗ.** Он фиксирует решение. Если решение меняет саму
  задачу — поправь тело через `edit_task`, иначе исполнитель прочитает старую
  формулировку и сделает то, от чего отказались;
* **реплика должна содержать варианты, а не только вопрос.** «Что делать?» —
  это перекладывание работы. «Вижу два пути: А даёт то-то ценой того-то, Б
  наоборот; рекомендую А, потому что...» — это обсуждение;
* **не пользуйся обсуждением как способом не делать работу.** Вопрос, на
  который ты можешь ответить сам, сходив и посмотрев, — не спорный вопрос.
  Сходи и посмотри.

Обсуждение читается в `get_task(id)` полем `messages` и доступно в любом
статусе: обсудить можно и задачу в работе, `discussion` нужен только тогда,
когда работа из-за вопроса встала.

## Как писать текст задачи

Задачу читает человек через неделю и другой ассистент через месяц. Оба не помнят
контекста, в котором ты её заводил.

**Заголовок** — что не так, конкретно. Не «Проблемы с каталогом», а
«Каталог: нет цены в карточке, прыгает вёрстка, переключатель без состояния».

**Тело** — по порядку:

1. **Когда и как найдено.** «Проверено 20.08.2026 живыми запросами, коды ответов
   настоящие». Это даёт следующему понять, устарело или нет.
2. **Факты с числами и адресами.** Не «description слишком длинный», а
   «description 182 знака при норме 160, обрежется в выдаче».
3. **Что делать.** Конкретные строки, конкретные файлы, если знаешь.
4. **Как проверить после правки.** Это самая забываемая часть, и она же решает,
   можно ли будет задачу закрыть без спора.

**Чего не делать:**

* не писать выводы, которых не проверял. Если факт не подтверждён — так и пиши:
  «требует проверки», а не утверждай. В трекере уже была снята задача, где
  «в разделе ноль автомобилей» оказалось неверным подсчётом: раздел был полон;
* не смешивать пять несвязанных дефектов в одну задачу, если чинятся они в разных
  местах. Общая причина — можно, общий файл — можно, «всё про каталог» — нет;
* не заводить дубли. `dedupe_key` при заведении пачкой обязателен.

### Ошибся в формулировке — правь тело, а не заметку

```
edit_task(id, body="...")     ← правильно
update_task(id, note="...")   ← неправильно, если это новая редакция ТЗ
```

Прошлая редакция сохранится в `result.history`, ничего не потеряется.

Почему это важно: пока править тело было нечем, уточнения складывались в
`result.reason`. В трекере до сих пор лежат задачи, у которых в `reason` полторы
страницы переписанного ТЗ, а тело осталось от первой редакции. Какой из двух
текстов действующий, не знает никто, и разбираться приходится человеку.

Задачу, которую завёл **человек**, ты не переписываешь: правка ляжет в
`result.proposed_edit`, и человек примет её сам. Ответ придёт успешный — смотри
в нём, изменилось ли поле на самом деле.

## Артефакты: результат работы кладётся при задаче

`attach_artifact(id, name, content, format)` — форматы `json`, `html`, `md`, `text`.

Клади сюда всё, что человек потом возьмёт руками: готовый JSON-LD, HTML-фрагмент,
таблицу замеров, отчёт. Раньше такого места не было, и собранная разметка уезжала
в Google Drive, где её никто не связывает с задачей.

* повторная заливка с тем же именем **заменяет** содержимое, а не плодит копию.
  `jsonld.json` должен быть один;
* для `format="json"` содержимое обязано парситься — сервер проверит. Битый JSON,
  пролежавший неделю, хуже отсутствующего: его найдут и применят;
* потолок 256 000 знаков. Это хранилище для разметки и отчётов, не для дампов;
* опись файлов приходит в `get_task` полем `artifacts`. Содержимое — отдельным
  вызовом `get_artifact(id, name)`, и только для того файла, который реально
  читаешь.

## Фронтенд и правки в коде

**Правки в репозитории вносит только ответственный исполнитель — один
назначенный LLM, а не любой ассистент, который подключился к MCP.** У тебя есть
доступ к трекеру; это не то же самое, что доступ к коду. Если ты не тот
исполнитель — твой результат по задаче это **ТЗ**, а не коммит.

Из этого следует, как оформлять задачи, затрагивающие фронтенд:

1. **Указывай репозиторий явно.** Их несколько, и «поправить на сайте» ничего не
   означает:
   * `avadge-site` — Django, шаблоны, вьюхи;
   * `avadge-site-django-front_dev` — Vite-сборка публичного сайта, SCSS и JS
     страниц;
   * `avadge-vue-frontend` — админ-панель на Vue.
2. **Указывай файл и место.** «Первый экран главной» — это
   `avadge-site/main/templates/components/index_banner.html` плюс стили в
   `avadge-site-django-front_dev/src/pages/index/`. Без пути исполнитель начнёт
   с поиска, а найдёт не то.
3. **Пиши, что именно поменять**, с текущими и целевыми значениями. «Сделать
   красиво» — не ТЗ. «H1 28px на мобильной, 40 на планшете, 56 на десктопе» — ТЗ.
4. **Фронтовую работу нельзя считать выполненной по факту правки исходника.**
   Она должна быть собрана и проверена в самом фронтовом репозитории, и только
   после этого попадает на сайт. Правка в файле, который не собран, на боевом не
   существует.
5. **Тип такой задачи — `ui` или `feature`**, то есть `[eye]`. Ты доводишь её до
   `confirmed`, принимает человек. Три ширины экрана и «выглядит правильно» ты не
   увидишь, и делать вид, что увидел, — худшее, что здесь можно сделать.

## Чего делать нельзя

| действие | почему |
|---|---|
| нажать «Применить» (`apply`) | пишет правки в живой контент сайта, это за человеком. Тебе — `propose_seo_changes` |
| принять, вернуть или снять чужую задачу (`owner` — не ты) | сервер откажет: приёмка за постановщиком или человеком. Тебе — `review` с отчётом |
| ставить `critical` на дизайн-хотелку | `critical` будит человека в Telegram; ложный пожар обесценивает очередь. `critical` — только когда сломано |
| закрыть задачу типа `ui` или `feature` | принимает человек, ты ставишь `confirmed` |
| закрыть `[self]` без `verified` | сервер откажет; и это единственное, что отличает проверку от «нажал и пошёл дальше» |
| ставить `done` или `confirmed` по локальной проверке | на боевом прежняя версия, человек открывает сайт и видит старое. До выкатки максимум `review` |
| писать в `verified` замер с localhost | это не проверка сайта, а проверка своей машины. Только `https://avadge.com` |
| выдумать тип | сервер откажет. Двенадцать штук, список выше |
| заводить находки чекеров руками | их заводит и закрывает чекер |
| писать новую редакцию ТЗ в `note` | тело задачи раздвоится, разбирать будет человек |
| закрыть родителя с живыми подзадачами | сервер откажет; иначе несделанные пункты исчезают вместе с ним |
| выйти из обсуждения без вывода | сервер откажет; спор начнётся заново через неделю |
| уносить в `discussion` то, что можно проверить самому | это не спорный вопрос, а несделанная работа |
| менять код, если ты не назначенный исполнитель | см. раздел выше |

Границы держит сервер, а не вежливость: `apply` и приём `[eye]`-задач отвечают
403 на ключ без сессии, приёмка чужой задачи — 403 на любой ключ, кроме
постановщика. Не трать шаги на подбор обхода — его нет.

## Инструменты

| инструмент | что делает |
|---|---|
| `tasks_whoami` | имя и префикс твоего ключа. Первый вызов сессии |
| `tasks_list_tasks` | список с фильтрами `status`, `priority`, `kind`, `source`, `parent`, `assigned_to_llm`, `owner` (`me`, префикс ключа или `none`). Страница — 10, это потолок |
| `tasks_get_task` | одна задача целиком: тело, `entity`, `owner`, `subtasks`, `messages`, опись файлов |
| `tasks_create_task` | завести. `kind` обязателен и строг, `priority` по правилам выше, `parent_id` делает подзадачу, `dedupe_key` против дублей. Постановщиком становится твой ключ |
| `tasks_update_task` | статус, приоритет, `note`, `verified`, взять в работу. Приёмочные статусы — только на своих задачах |
| `tasks_edit_task` | заголовок, описание, тип, `entity`, родитель — с сохранением прошлой редакции |
| `tasks_post_message` | реплика в обсуждение задачи |
| `tasks_attach_artifact` | приложить файл к задаче |
| `tasks_get_artifact` | прочитать приложенный файл |
| `tasks_get_seo_page` | текущие SEO-поля страницы. Читай ПЕРЕД тем, как предлагать правку |
| `tasks_propose_seo_changes` | предложить правку SeoPage и уйти в `review`. Только для `seo_meta` |

В списке `body` обрезан до 100 знаков — полное описание берётся `get_task(id)` и
только для той задачи, которую реально собираешься делать. Нужен другой срез —
это фильтр, а не страница побольше.
